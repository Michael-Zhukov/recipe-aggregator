# REFACTORING — Recipe Aggregator

## 1. Мета рефакторингу

Метою роботи є перетворення неідіоматичного коду обробки рецептів на структуроване доменне ядро проєкту Recipe Aggregator.

Під час рефакторингу використано сучасні можливості Python: `dataclass`, генератори, `Counter`, множини, анотації типів, `pathlib` і контекстні менеджери.

## 2. Виявлені дефекти та їх усунення

| № | Було | Стало |
|---|---|---|
| 1 | `open()` без `with` | `with path.open(encoding="utf-8")` |
| 2 | `while` з ручним лічильником | Ітерація `for` |
| 3 | Посимвольне перетворення рядка | `lower()` і `split()` |
| 4 | Порівняння `!= None` | Перевірка `is not None` |
| 5 | Загальний `except:` | `except (TypeError, ValueError)` |
| 6 | Зберігання рецептів у списках | Модель `Recipe` через `@dataclass` |
| 7 | Вкладені цикли дедуплікації | Множина `seen` |
| 8 | Ручний підрахунок інгредієнтів | `collections.Counter` |
| 9 | `print()` усередині обробки | Виведення перенесено до `cli.py` |
| 10 | Одна функція виконує всі операції | Розділення на `domain`, `sources`, `services`, `cli` |
| 11 | Неінформативні назви змінних | Зрозумілі імена `recipe`, `rows`, `seen` |
| 12 | Відсутність анотацій типів | Додано `Recipe`, `Iterator`, `Iterable`, `Path` |

## 3. Структура після рефакторингу

- `domain/models.py` — модель предметної області `Recipe`.
- `domain/parsing.py` — нормалізація та перетворення записів.
- `sources/json_file.py` — читання JSON та JSONL.
- `services/pipeline.py` — дедуплікація, статистика та конвеєр обробки.
- `cli.py` — консольний інтерфейс користувача.

## 4. Свідомі зміни поведінки

У старому коді некоректне значення часу приготування перетворювалося на `0`.

Після рефакторингу функція `parse_cooking_time()` повертає `None`.

Це дозволяє розрізняти невідомий час приготування та фактичне значення нуль хвилин.

Для видалення дублікатів використано множину ключів `seen`, яка дозволяє зберегти початковий порядок записів. На відміну від `set(recipes)`, порівняння виконується лише за назвою рецепта та категорією.

## 5. Порівняння продуктивності

Для вимірювання використано файл `data/large.jsonl`, який містить 200 000 записів рецептів.

Порівнюються два способи обробки:

- Генератор — построчне читання без накопичення всіх записів.
- Список — завантаження всіх записів у пам'ять.

| Спосіб | Кількість записів | Час, с | Пікова пам'ять, МБ |
|---|---:|---:|---:|
| Генератор | 200 000 | 1,36 | 0,2 |
| Список | 200 000 | 1,50 | 126,0 |

Вимірювання виконуються за допомогою `time.perf_counter()` та `tracemalloc`.

Генератор дозволяє значно зменшити використання оперативної пам'яті під час обробки великих файлів.

## 6. Тестування

Для перевірки використано `pytest`. Реалізовано характеризаційний тест старого коду та тести нормалізації, читання JSON, дедуплікації і конвеєра.

Перевірка якості коду здійснюється за допомогою Ruff.

Результати перевірки:

- Ruff: All checks passed!
- Pytest: 9 passed.
- CLI: реалізовано виведення кількості унікальних
  рецептів і статистики основних інгредієнтів.

## 7. Характеризаційне тестування

Перед початком рефакторингу створено характеризаційний
тест для фіксації поведінки початкового модуля.

Тест перевіряв:
- нормалізацію назв рецептів;
- видалення дублікатів;
- пропуск записів із порожньою назвою;
- перетворення нечислового часу приготування на 0.

Після рефакторингу тест адаптовано до нової реалізації.

Свідомою зміною поведінки стало повернення None
замість 0 для невідомого часу приготування.

## 8. Особливості дедуплікації

Для видалення повторюваних рецептів використано
множину seen, яка зберігає ключі оброблених записів.

Ключ складається з назви рецепта та категорії.

Такий підхід забезпечує очікувану часову складність
O(n) замість O(n²) у початковій реалізації.

Використання генератора yield дозволяє зберегти
порядок першої появи рецептів у вихідних даних.
